# 同步治理提案：怎么让六个分支不再乱（2026-08-30）

> 前置阅读：`FAMILY_TREE_2026_08_30.md`（现状实测）。
> 本文是**思考与建议**，不是已执行的动作。所有建议都标注了代价，由维护者裁决。

---

## 0. 「乱」的病理诊断

把这些天的痛感归纳成四个具体病因，每个都能对到实例：

| # | 病因 | 实例 |
|---|---|---|
| P1 | **同步单位是「分支」而不是「特性」** | renov 01a04ea3 想要 PIP，只能整个盯着 refab 01a04e96 的 18 个混装提交挑 |
| P2 | **从未合并的工作分支取货** | renov 26.2 的 PIP 正式代码，源头是 refab 一条还在天天变的 arena 分支 |
| P3 | **handoff 有生产无回执** | renov 04ea3 给 26.1.2 写了补课包（含 1678 行蓝本），但 26.1.2 侧谁接、接没接、接到哪，任何仓任何文件里都查不到 |
| P4 | **平行竞争实现无裁决机制** | renov 26.2 同时存在 369 行精简 PIP（04ec0）与 1126 行全量 PIP（04ea3），互不知情地共存了两天 |

以及一个背景放大器：**六个长期分支 × 两个纪元 × 两种加载器**，任何一个特性
理论上有最多 6 个落点，但没有一张「哪些落点该有、哪些落点已有」的登记表——
§4 的矩阵是本次人肉盘出来的，之前不存在。

## 1. 总原则：承认「谱系不对称」，放弃全对称同步

六个分支不是平等的。按实测现状，它们天然分成三层：

```
创新层   refab 26.2(main) + arena/01a04e96     ← 新特性只在这里出生
         （渲染 API 最新、特性最全、动得最快）
                    │ ①纪元内跨加载器：语义搬运（成本低）
适配层   renov 26.2                            ← 第一同步目标
                    │ ②跨纪元：重新设计（成本高，一事一议）
存量层   refab/renov 的 26.1.2 与 1.21.11       ← 只收「修复」，原则上不收「特性」
         （深度孔径纪元，架构已冻结）
```

**建议的第一原则：特性只在创新层出生；存量层默认只接收 bug 修复与
纪元内可平移的机制（如 final-overlay），大型特性（rerender PIP、meshloader）
是否跨纪元移植一事一议、默认不做。**

这条如果被接受，立刻消掉一半的同步义务：meshloader、镜内裁手/裁字、
PIP rerender 都不再欠 26.1.2/1.21.11 各两份债。1.21.11 上正在做的
rerender 移植（refab 052b2 的 TEMP 诊断轮）就成了一个需要明确
「继续/止损」裁决的点——它正在做的事，恰是本原则默认不做的高成本跨纪元移植。
（也可以裁决为例外继续做——但要明确它是例外，而不是先例。）

提交历史已经天然按域成簇，不需要 rebase 重排。）

### 2.2 同步只认里程碑

**建议规则：跨仓/跨分支同步的取货点，只能是目标特性已并入长期分支后的
merge commit（或 tag）**。同步文档里的「源头」一栏必须写这个 commit。

- 好处：姊妹仓不再追着活分支跑；「同步自 XX」的引用永远可复现。
- 已发生的例外（renov 04ea3 已从活分支取了 PIP）不必回滚，但在 PR A-D
  并入后，renov 侧应把同步基准**重新锚定**到 main 的 merge commit，
  校对一遍活分支后续变化（本轮就有：`9df8718` 改了 ResolutionScale 语义、
  `4ec0dde` 退休了 scope-pass poly skip——04ea3 若照旧版同步就带走了死代码）。

## 5. 建议的固定节拍（把同步变成例行公事）

1. **特性完成** → 实机 PASS → 按域 PR 并入所在长期分支（§2.1）;
2. **并入时**顺手更新特性矩阵（`FAMILY_TREE` §4 那张表，建议单拆成
   `FEATURE_MATRIX.md` 两仓镜像）——这张表就是「还欠谁什么」的账本;
3. **需要姊妹侧跟进的**，写 handoff + 在 LEDGER 登记 OPEN;
4. 姊妹侧开工时标 CLAIMED(分支)，完成时标 DONE(commit);
5. 每次发版（R 系列 tag）前，扫一遍 LEDGER 的 OPEN/CLAIMED——没清的要么进发版说明
   的已知差异，要么阻塞发版，不允许「不知道」。

每步都只是在现有习惯上加一行登记，没有新工具、新流程负担。

## 附：为什么不建议的两个「大招」

- **Monorepo / 子模块统一两仓**：两仓无共同 git 祖先、加载器骨架不同、
  发版节奏不同，强行统一只会把语义同步的成本转嫁成合并冲突的成本。
  当前「语义同步 + handoff」模式本身是对的，缺的只是登记，不是缺架构。
- **自动同步机器人 / cherry-pick 流水线**：无共同祖先导致 cherry-pick 根本不可用
  （refab 的 SYNC 文档已实测注明 merge-base 为空）；语义搬运必须过人/agent 的手，
  自动化只能自动化「提醒」（LEDGER 有 OPEN 超 N 天冒泡），不能自动化「搬运」。
