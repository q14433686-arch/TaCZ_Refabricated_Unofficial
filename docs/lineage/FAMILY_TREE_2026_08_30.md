## 1. 两大纪元：为什么不能一套代码走天下

整个家族按**渲染架构**分成两个纪元，这是所有同步混乱的根源，必须先接受它：

| | 掩码/PIP 纪元（26.2） | 深度孔径纪元（1.21.11 / 26.1.2） |
|---|---|---|
| 镜片判定 | `ScopeMaskRenderer` 目镜掩码（离屏 R 通道） | 深度孔径 `ad < wd - eps`（深度比较） |
| PIP | 二次世界渲染（`ScopePipRenderer` ~1126-1419 行）+ 可配分辨率 | 屏幕空间重投影（Step-3），分辨率数学锁死 |
| 渲染 API | 26.2 render-state 体系（`GameRenderState`、8 参 `LevelRenderer#render`） | 旧 API（`renderItemInHand(float,boolean,Matrix4f)`） |
| 光影下准星/遮光环 | PIP 合成后重画（refab `4168e91`、renov `0c446f4`） | Iris final composite 后重画（final-overlay 机制，起源 refab 1.21.11 `2710c7c` 一族） |
| meshloader (TML) | 仅 refab arena/01a04e96 有 | 无 |

**推论**：
- 纪元内跨加载器（refab 26.2 ↔ renov 26.2）同步是「同 API 面、不同 mod 骨架」，
  语义可整段搬，只换事件/注册/mixin 表皮。
- 跨纪元移植（26.2 → 1.21.11）是**重新设计**，不是同步——refab 1.21.11 的
  rerender 移植计划文档（`SCOPE_PIP_RERENDER_1211_PORT_PLAN_20260830.md`）
  已经把这一点写透：25+ 文件、逐 API 断点适配、无法盲写。
- 同一个 bug 会以「同源不同形」出现在两个纪元
  （例：遮光环被盖——26.2 是被*自家 PIP 合成*盖，深度孔径是被*光影后置 pass*盖，
  解法同构但代码不同）。renovated 侧的 handoff 文档已总结过此规律。

### 2.3 文档体系差异（同步时的认知负担来源之一）

- refab：`docs/` 平铺大量 `*_2026_MM_DD.md` 专题文档 + `docs/handoff/` + `docs/archive/`；
  编年史式，全景但翻找成本高。
- renovated：`AGENTS.md`+`CHARTER.md` 宪法 + `docs/WP*_EVIDENCE.md` 工作包证据链 +
  `docs/records/` + `docs/handoff/`；工单式，验证纪律更严
  （`check_release_consistency.sh --strict` 门禁、红线清单编号到 8）。
- 两边**都在用 handoff 文档跨仓传递工作**，且质量很高（renovated 侧甚至预打包了
  1678 行蓝本 diff + 移植契约），但 handoff 的**消费状态没有登记**——
  谁读了、做没做、做到哪，只能靠翻分支猜。这是「乱」的第二大来源。

## 5. 三个当前最值得注意的事实

1. **跨仓同步已经从「未合并的 arena 分支」直接取货**：renov 01a04ea3 的 PIP
   同步源头是 refab `arena/01a04e96`（本分支）——而本分支至今未并入 `26.2(main)`。
   这意味着姊妹仓的正式代码依赖着我们一条随时在动的工作分支。风险与对策见治理提案 §2。
2. **renov 26.2 存在两条平行 PIP 实现**（04ec0 精简版 vs 04ea3 全量版），
   一旦两条都往前走，将来合并必打架。需要尽快裁决（提案 §3）。
3. **本分支（01a04e96）已经积到 18 个实质提交、横跨 4 个互不相关的特性域**
   （meshloader、PIP 配置、检视动画、镜内裁剪）——它本身就是「乱」的样本：
   任何姊妹分支想同步其中一项，都得从 18 个提交里人肉摘。拆分建议见提案 §2。
