| `db62d25` §4.2：`GunSmithTableBlockB` 创造模式「抑制另一半掉落」的判据写反 | **回移（新）**。本线 `GunSmithTableBlockB` 与 26.2 修前逐字相同。战利品表（`workbench_b.json` / `gun_smith_table.json`）的产出条件是 `part=foot`，所以要在玩家那一半被移除**之前**把会产出的 FOOT 用 `setBlock` 静默拿掉 —— 守卫应挂 HEAD、拿掉 FOOT；旧代码是 `bedPart == FOOT`（照抄原版 `BedBlock`，而原版床的 loot 条件在 head，方向正好相反）。已改。C 工作台（`lower` 产出、守卫挂 `upper`）本来就对，未动。**与 26.2 文档的一处出入**：26.2 的调查记录说「创造模式挖 foot：无掉落」；按 1.21.11 反编译的 `ServerPlayerGameMode#destroyBlock` → `Level#setBlock`（向邻居传播用 `flags & -34`，会清掉 `UPDATE_SUPPRESS_DROPS`）→ `Block#updateOrDestroy` 逐步推演，旧代码挖 FOOT 时先静默清掉 HEAD，FOOT 随即经 `updateShape→AIR` 自毁并走自己的战利品表，**也会漏出一个**，所以创造模式挖任意一半都漏。结论（要翻判据）一致，只是旧行为的描述不同；两者都是静态推演，未实机。 |
| `25c0adc`：雕像上的枪随方块消失 —— 覆写 `BlockEntity#preRemoveSideEffects` | **回移**。本线 `StatueBlockEntity` / `StatueBlock` 与 26.2 修前逐字相同（除 `TYPE` 写法），`dropItem()` 无任何调用点。1.21.11 里同样没有 `Block#onRemove`（`BlockBehaviour` 只剩 `affectNeighborsAfterRemoval`），`BlockEntity#preRemoveSideEffects(BlockPos, BlockState)` 存在且默认实现只倒空 `Container`；调用点是 `LevelChunk#setBlockState`（旧状态带方块实体、方块种类变了且新状态不要求保留方块实体、标志位无 `UPDATE_SKIP_BLOCK_ENTITY_SIDEEFFECTS`，仅服务端），爆炸路径上 `BlockBehaviour#onExplosionHit` 默认实现最终是 `setBlock(AIR, 3)`，也会触发。代码与 26.2 一致：覆写 + `dropItem(BlockState)` 私有重载（移除时点缓存状态可能已是空气，取 `FACING` 会抛）。26.2 文档说「客户端也会走移除流程」，1.21.11 的调用点本身已限定服务端，覆写里的 `isClientSide` 判断只是防御。 |
| `25c0adc`：标靶主人重启后丢失 —— `loadAdditional` 的前置判据读 `Owner`，`saveAdditional` 写 `owner_uuid`/`owner_name` | **回移症状，按本线改修法**。键不对称这一点本线同样存在（修前与 26.2 逐字相同），而且客户端的方块实体也靠 `loadAdditional` 吃更新包，所以连客户端都读不到、头像画不出来。**但 26.2 的修法建在一个在本线不成立的前提上**：它假设档案可以是「只有名字、没有 UUID」的 `GameProfile`（`new GameProfile(null, 名字)`）。本线依赖 `authlib-7.0.61`，`GameProfile` 是 record，构造器拒绝 null —— 2026-10-27 用 CI 的 `compileJava` 前置阶段对该 jar 反射实测（探针提交 `0909502f`；输出留在 CI 回推的日志提交 `d6f52ab6` 的 `build-reports/compile-java.log` 里；探针已在 `ba453eb8` 移除）：`new GameProfile(null,"probe")` → `NullPointerException: Profile ID must not be null`；`new GameProfile(uuid,null)` → `Profile name must not be null`；空串名与含空格 / 中文 / 超 16 字符的名字都能构造。所以「名字-only 的 GameProfile」在本线根本造不出来，下一行的 NPE 才是更早的问题。处置见下两行。 |
| 本线额外发现（26.2 未改）：`TargetBlock#setPlacedBy` 与 `TargetMinecart#getGameProfile` 里的 `new GameProfile(null, 名字)` | **本线新修**。运行期必抛 NPE，编译期看不出：放置改过名的标靶会在 `setPlacedBy` 里中断（名字与头像都设不上；`BlockItem#place` 里 `setPlacedBy` 排在 `consume(1)` 之前，异常还会让物品不被消耗）；改过名的标靶矿车的 `getGameProfile()` 在客户端 `extractRenderState` 里每帧调用 ⇒ 渲染线程崩溃。改为原版的 `ResolvableProfile`（可以只有名字），统一入口 `util/TargetOwnerProfiles#fromName`；`TargetBlockEntity` 只存读 `owner_name` 一个键（旧的 `owner_uuid` 被忽略，UUID 由客户端按名字重新解析；存档里已有的 `owner_name`（如 26.2 线写出的）照常读取，本线修前其实写不出主人；反方向——26.2 线读只含 `owner_name` 的存档——会走它自己那条 `new GameProfile(null, 名字)` 分支，见下一句的复核请求）；`TargetMinecart#getGameProfile` → `getOwnerProfile`。**26.1.2 / 26.2 / 26.3 / 26.4 四条线的 `TargetBlock` 与 `TargetMinecart` 现在仍是 `new GameProfile(null, …)`（已逐分支核对源码）；26.2 修后的 `loadAdditional` 还多一处 `new GameProfile(tryParseUuid(…), name 或 null)`。26.x 的 authlib 是 9.x，我没有对它做同样的实测，但 null 检查在 authlib 6.0.52 已有公开崩溃日志（Taterzens #179）、本线 7.0.61 已实测，请各线用同一个探针复核后再决定。** |
| `39ccef6` / `8e56a87`（含 5 个临时编译探针）：标靶头像「名字 → 皮肤」—— 服务端经 `Services#nameToIdCache` 解析 UUID、`setLevel` 触发、`profileResolveAttempted`；客户端 `TargetRenderer` 改用 `SkinManager#createLookup(profile, false)` | **不移植，用本线能成立的做法替代**。三个理由：① 前提（null UUID 档案）在本线不成立，见上；② 1.21.11 的 `SkinManager#get` 自身不发起任何按名字 / 按 UUID 向会话服务查人的调用，只处理档案**已经带着**的 `textures` 属性；26.2 那条服务端解析只补出 UUID（没有 `textures`，也不会被存档或同步给客户端 —— `saveAdditional` 只写 id 与 name），客户端拿到后仍是默认皮肤，所以那条链在本线不会产出真皮肤；③ 原版 1.21.9+ 的做法是：方块实体只存 `ResolvableProfile`、**服务端不解析**（`SkullBlockEntity` 即如此），客户端渲染时经 `Minecraft#playerSkinRenderCache()`（`PlayerSkinRenderCache#getOrDefault`）异步按名字解析并缓存，未就绪先给默认皮肤。本线照此实现：新增 `client/renderer/other/TargetOwnerSkins`，`TargetRenderer` 与 `TargetMinecartRenderer` 共用，任何运行期异常退回默认皮肤。26.2 的 5 个探针提交是它们在 26.2 API 上确认类型用的临时件，本线的 API 事实改由 1.21.11 反编译源码核对、再交 CI 编译确认，不需要。 |
| `c2c458f`：两个方块守门脚本接入 `build.yml`，同步镜像与文档 | **回移脚本，适配后接入**：`scripts/verify_block_drops.py`（A 方块类禁手工 `popResource`；B 战利品表旧 schema + 根半边条件；C `isRoot()` 与 loot 一致；**D（本线新增）创造模式抑制判据必须挂在非根半边**）与 `scripts/verify_block_entity_persistence.py`（A 判据键必须被写入；B 读写键对称；C 持有 `ItemStack` 的方块实体必须有 `preRemoveSideEffects`；D 禁 `onRemove` 覆写；**E（本线新增）禁止 `new GameProfile(..., null, ...)`**）。均已对修前 / 修后的本线源码树各跑过一遍（见下）。`scripts/verify_263_sync_baseline.py` 原先按方法体切片检查「不得 popResource」，覆写删掉后会 `IndexError`，已改成整类去注释后检查。已接入 `build.yml`（本会话的凭据可以直接推送 workflow，见「CI 结果」一节）。 |
| `78de13b`：26.2 `mod_version` 升 R3-hotfix4 | **不跟**：升版本号是发版决定，本轮没有要求。本线保持 `1.1.8+fabric.1.21.11.R3-hotfix3`。若要对齐，需另起独立提交同步 `gradle.properties`、`fabric.mod.json` 与根 README 的 6 处，并以 `bash scripts/check_release_consistency.sh --strict` 收尾（`AGENTS.md` §1）。 |

## 验证 / 边界

- **静态脚本（沙箱可跑，已跑）**：
  - `python3 scripts/verify_block_drops.py --strict`：修后通过；把 `GunSmithTableBlockB` 还原成修前版本 ⇒ D 项报两条（守卫挂在根半边、拿掉的邻居是 head）；往 `AbstractGunSmithTableBlock` 注入一条 `popResource` ⇒ A 项报错；改坏战利品表 / `isRoot()` ⇒ B / C 项报错。
  - `python3 scripts/verify_block_entity_persistence.py --strict`：修前的本线源码树报 5 项（雕像缺钩子、标靶判据键、标靶只读不写、`TargetBlock` 与 `TargetMinecart` 各一处 `new GameProfile(null, …)`）；修后通过。
  - `python3 scripts/verify_263_sync_baseline.py`、`verify_bullet_hole_orientation.py`、`verify_recipe_viewer_reload.py`：通过。
- **编译**：沙箱无 JDK，交 GitHub Actions，结果见下一节「CI 结果」。
- **API 事实的来源**：1.21.11 的 `BlockEntity#preRemoveSideEffects`、`LevelChunk#setBlockState`、`Level#setBlock` / `destroyBlock`、`Block#updateOrDestroy`、`ServerPlayerGameMode#destroyBlock`、`SkinManager`、`PlayerSkinRenderCache`、`ResolvableProfile`、`SkullBlockEntity`、`BlockItem#place` 是对第三方公开的 1.21.11 反编译源码（GitHub `RecaniteButOnGit/Minecraft-1.21.11`）逐处阅读，并与 `FabricMC/yarn` 1.21.11 映射（`BlockEntity#onBlockReplaced = method_66473`）互证；不是官方源码，且仍以 CI 编译为最终确认。`GameProfile` 的行为是对本分支实际依赖的 jar 的反射实测，不依赖上述反编译。
- **没有做**：任何进游戏的验证。`preRemoveSideEffects` 是否真的在各条移除路径上掉枪、创造 / 生存的工作台掉落数量、改名标靶的头像在真实玩家名下能否换成真皮肤（依赖客户端能访问 Mojang 会话 / 档案接口，离线服与断网只会是默认皮肤）、标靶矿车改名后不再崩溃，都**没有实机证据**。不能把本轮写成「已修复」，只能写成「静态推演 + 编译（待 CI）」。
