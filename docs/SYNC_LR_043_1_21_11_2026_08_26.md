## 1. 采纳的五个单元（全部落在 LRTactical 层，不碰瞄准镜架构）

### A · 投掷物引信：预燃拉满后扔出永不爆炸

本分支同样存在此 bug（三处联动病灶均已核实）：

- `ThrowableItemEntity#tick`：判定原为 `tickCount >= life && life > 0`，
  与 `ThrowableItem#onThrow` 的 `setLife(max(life - cooked, 0))` 冲突 ——
  预燃拉满时剩余引信被 clamp 到 0，`life > 0` 永不成立。
- `ThrowableItem#onUseTick`：手上引爆门槛原为自创的 `lifeTime * 0.9`。
- `UsingProgressOverlay`：红条分母同样是 `life * 0.9`。

改动（与源提交一致，三处联动 + 两道 `-1` 防线）：

1. `tick` 判定改为 `life >= 0 && tickCount >= life`。
   `life < 0` 仍永不超时 —— C4 / 遥控起爆（`life_time = -1`）的约定。
2. `onUseTick` 门槛改为完整 `lifeTime`（官方 0.4.3 无 10% 余量），
   并在开头对 `maxCookTime <= 0` 直接 `return`（`-1` 的 C4 不参与手上引爆）。
3. `onThrow` 的 cook clamp 加 `throwable.getLife() >= 0` 前置，
   防止 `-1` 被抬成 `0` 导致落地下一 tick 自爆、遥控起爆失效。
4. `UsingProgressOverlay` 红条分母同步改为完整 `lifeTime`。

### B · 投掷物不再吃到近战的 `INPUT_IDLE`

`LrTickAnimationEvent#tickAnimation(Minecraft)` 的入口判定从
`AnimateGeoItemRenderer<?, ?>` 收窄为 `MeleeItemRenderer`（与官方 LR 一致）。
`GunAnimationConstant.INPUT_IDLE` 字面量是 `"idle"`，官方手雷脚本用它表示
**取消拔销**；此前每 tick 广播会把静止拔销的 `unlock_safe` 反复掐断。
第三人称 `visualUpdate` 路径未动，仍覆盖近战/投掷物/消耗品三类；
`isLrAnimatedItem` 按源提交补入 `ConsumableItemRenderer`。

### C · 烟雾粒子全亮 → 环境光采样

写死的 `15728880`（0xF000F0）改为采 `LightLayer.SKY` / `LightLayer.BLOCK`，
两者都 ≤2 时扫六个邻格取较大值，最后各自保底 2，返回 `sky << 20 | block << 4`。

**本分支特有的方法名适配**：覆写的方法是 **`getLightColor(float)`**
（1.21.1 上游同名；26.2 才改名 `getLightCoords(float)`）。若照抄 26.2 的
方法名，`@Override` 会编译失败，或漏写 `@Override` 变成永不被调用的死方法。
本次保留 `getLightColor`，只替换方法体；原文件里「上游覆写的是 getLightColor，
但 26.2 的 Particle 上只有 getLightColor」这句自相矛盾的注释（从 26.2 复制后
改漏）已一并修对。

API 核实：`BlockAndLightGetter#getBrightness(LightLayer, BlockPos)I` 用
26.1.2 分支跟踪的 merged jar 逐字节码确认存在于继承链（1.21.11 为更早版本，
该 API 自 1.14 光照重构后一直稳定）；`BlockPos.containing` /
`BlockPos#relative(Direction)` 在本分支已有使用先例（`BlockRayTrace`、
`GunSmithTableBlockB` 等）。

### D · `display_offset` / `entity_transform`

新增 `DisplayTransform` 工具类；`MeleeDisplayInstance` / `ThrowableDisplayInstance`
各补 `displayOffset` 字段 + getter + record 组件 + `create()` 赋值
（Throwable 另补 `entityTransform` 与 `entity_transform` record 组件 ——
字段与 record 组件同一次改完，不重蹈姊妹仓 `305bed1` 补刀的覆辙）。
`MeleeItemRenderer` / `ThrowableItemRendererWrapper` 在 `transforms` 之后、
ZP180 翻转之前施加 `display_offset`；`ThrowableEntityRenderer` 在 extract
阶段快照 `entity_transform`，**有内容包 display 时**走官方姿态（`YP` 偏航 +
`entity_transform`），否则保持本分支原有占位姿态（`YN` + `translate(0,0.15,0)`
/ `(0,0.35,-0.15)`）——占位分支画原版物品贴片，套官方参数会沉进地里。

`LrClientAssetsManager` 的 `GSON` 注册 `Vector3f` 适配器（复用本分支已有的
`com.tacz.guns.client.resource.serialize.Vector3fSerializer`，已核实存在），
否则 `display_offset` 数组会抛 `JsonSyntaxException`，而 `create()` 的 catch
是整文件粒度，一份 display 会整体消失。

**本分支 `ItemTransform#apply` 半格偏移核实**：`MeleeItemRenderer#renderByItem`
的既有注释已写明本环境的 `apply` 内部自带 `translate(-0.5,-0.5,-0.5)`
（调用方预先 `translate(0.5,0.5,0.5)` 抵消）——与 26.2 结论一致，
`DisplayTransform.EntityTransform#apply` 手写平移/旋转/缩放三步的取舍不变，
注释已按本分支措辞。`entity_transform` 的量纲不统一（JSON 像素 ×1/16、
默认值方块单位）是官方既成契约，如实保留。

### E · 消耗品 Bedrock/Lua 渲染层

新增 4 个类 + 接线（与本分支环境对齐，全部静态核实过依赖存在）：

- `api/animation/ConsumableAnimationStateContext`：继承
  `BaseAnimationStateContext`（本分支已收敛 `currentItem` / `getStackCount()`
  / 全套输入查询，已核实），不是姊妹仓的直接继承 `ItemAnimationStateContext`。
- `client/renderer/item/ConsumableItemRenderer`：与 `MeleeItemRenderer` 逐段平行；
  **注意本分支 `ItemTransforms` 仍在 `net.minecraft.client.renderer.block.model`
  包**（26.2 已迁到 `client.resources.model.cuboid`），import 已按本分支适配。
- `client/resource/display/ConsumableDisplayInstance`（同上 import 适配）。
- `client/resource/manager/ConsumableDisplayManager`：**覆写
  `getFabricDependencies()`**（Fabric 并行重载必需，缺了会偶发
  "no corresponding model found"；姊妹仓 NeoForge 版没有此覆写，不可照抄）。
- 接线：`LrTacticalAPI#getConsumableDisplay`、`LrClientAssetsManager`
  第三个 manager/getter/path 回退、`HasCustomDisplayProperty` 第三类、
  `ModEntitiesRender#registerItemRenderers` + `CONSUMABLE`、
  `ConsumableItem implements cn.sh1rocu.tacz.api.extension.IItem`
  （本仓 Fabric 扩展点，已核实存在；**不是**姊妹仓 NeoForge 的
  `ILrItemExtension`）+ `getCustomRenderer` + `tacz$onEntitySwing`。
- `register.accept(consumableDisplay)` 为单参形式（本仓 manager 自带
  `getFabricId()`）。

## 2. 前置缺口：补齐 `assets/lrtactical/items/*.json` 与 `models/item/*.json`

**核实结果**：本分支（与 26.1.2 分支）此前**一个** `assets/lrtactical/items/*.json`
与 `assets/lrtactical/models/item/*.json` 都没有（`git ls-tree` 为空）——
尽管代码里 `LrDynamicItemModel` / `HasCustomDisplayProperty` 与
`registerItemModels()` 均已就位。

**是遗漏，不是版本契约不同**：

1. 本分支代码在物品 JSON 解码前注册 `ItemModels.ID_MAPPER.put(lrtactical:dynamic_item)`
   与 `ConditionalItemModelProperties.ID_MAPPER.put(lrtactical:has_custom_display)`，
   注释（`MeleeItem`、`HasCustomDisplayProperty`、`TaczDynamicItemModel`）
   全部按 `items/*.json` 契约描述 —— 1.21.11 属于 1.21.4 之后，沿用该契约。
2. `resources/tacz-26.1.2-source-and-resource-bundle.jar`（26.1.2 的构建产物）
   里**带着**这 10 个文件（melee/throwable 已是条件分流版）——上游构建有，
   本分支源码树没有，属移植/清理时的遗漏。

因此本次按交接要求的顺序补齐：

1. `items/melee.json`、`items/throwable.json`（`minecraft:condition` +
   `lrtactical:has_custom_display` 分流：有内容包走 `lrtactical:dynamic_item`，
   没有则回退占位模型）；
2. `items/detonator.json`（无 Bedrock 管线，直接占位模型）；
3. `items/consumable.json`（本次同步新增的条件分流版，含 `oversized_in_gui`）；
4. 配套 `models/item/{melee,throwable,consumable,detonator}.json` 占位模型
   （全部复用原版纹理：铁剑/雪球/药水/红石，不含任何上游 ARR 美术资源）与
   `models/item/{melee,throwable,consumable}_dynamic.json` 动态 base
   （无 parent，只有 `particle` + `gui_light`，理由同 26.2 注释）。

**如实说明影响**：补齐前，这些物品在本分支构建里没有任何物品模型定义；
补齐后，无内容包时它们渲染为原版占位图标，有内容包时进入
`lrtactical:dynamic_item` 管线。这对既有行为是**修复缺口**而非「保持原样」，
JSON 注释按此事实书写。

## 4. 验证状态 —— 不标 PASS

- **本沙箱无法编译**：环境里没有 JDK，且到 Maven / Mojang / Gradle 的网络
  均不可达，`./gradlew build`（含混淆分支关键的 remap 阶段）**没有跑过**。
  源分支同样没跑过编译。
- `docs/verify_mixin_targets.py` 与 `docs/verify_shader_imports.py` 需要
  Loom 的 merged jar（`./gradlew help` 产物），同样**没法跑**。
  缓解事实：本批**没有新增/修改任何 mixin 目标，也没有碰任何 shader**，
  两个脚本的检查面对本批改动为空。
- 已做的静态核对（替代编译）：
  - 全部改动逐文件与源提交 `630ef87` 比对，差异仅限本分支适配项
    （`getLightColor` 方法名、`ItemTransforms` 包名、注释措辞）；
  - 新引用的每个类型/方法都在本分支源码树找到先例或声明：
    `Vector3fSerializer`、`BaseAnimationStateContext`（currentItem/
    getStackCount/输入查询）、`IItem`（getCustomRenderer/tacz$onEntitySwing）、
    `JsonDataManager` 及 `getFabricDependencies`（`MeleeDisplayManager` 同型）、
    `IConsumable#getDisplayId`、`ConsumableData#getPutAwayTime`、
    `ModItems.CONSUMABLE`、`SubmitNodeCollector`/`RenderTypes`/`SlotModel` 等；
  - `getBrightness(LightLayer, BlockPos)` 以 26.1.2 merged jar 字节码确认
    （见 §1 C）；
  - 11 个新 JSON 全部通过 `json.load`；20 个改动/新增 Java 文件通过括号配平检查。

**结论：未验证，不得标 PASS，不得写 "fixed"。** 合并/发版前必须：

1. `./gradlew build`（混淆分支重点看 remap 阶段）；
2. `python3 docs/verify_mixin_targets.py` 与 `python3 docs/verify_shader_imports.py`；
3. 实机复测（清单见下）。
