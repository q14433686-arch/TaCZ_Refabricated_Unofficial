# 延后设计：长按 R 的实体供弹器选择轮盘

> **状态：未实现、未注册输入钩子。** 本文只保存已经确认的设计边界，不能把它当作当前版本的功能说明。

## 当前行为

- `R` 在 **按下** 时立即走原有换弹逻辑；不会等待按键松开，也不会因为手中枪使用实体弹匣/弹链而延迟。
- 已审计的外置实体供弹器仍由服务端按正常策略选择兼容且余弹最多的载具，并在真实动画供弹点执行原有库存事务。
- `Shift + R` 的人工退匣/退漏夹路径保持原有各自的服务端逻辑。
- 当前没有轮盘 HUD、没有长按计时、没有“选定槽位”网络字段，也没有客户端可指定弹匣槽位的旁路。

这样单点 R 不会再被轮盘预判吞掉或拖到松键后才开始换弹。

## 已记录、待以后重新确认的交互意图

此前确认的目标交互是：**长按 R → 选择一件真实实体载具 → 松键/确认后立刻以该载具换装。** 在真正恢复开发前，仍须重新确认按住阈值、确认方式、取消方式、鼠标/手柄交互和超过一页候选时的翻页方式；本文不把旧的固定 tick 数当作产品承诺。

拟议轮盘只改变“选择哪一件真实载具”，绝不改变供弹、扣弹、动画或库存的服务端权威性：

1. 只向玩家展示背包中真实存在的、与当前枪和当前供弹定义兼容的实体载具；候选至少按 `MagazineFamily`、`MagazineAmmoId`、容量和 `FeedDeviceKind` 区分。
2. 每种弹药 profile 保持独立 `AmmoId`、独立散装弹和独立服务端弹道；同 canonical calibre 的 profile 可以按真实顶部顺序混装进同一实体载具。轮盘必须显示下一发与混装统计，不能只换名称或附件图标。详见 [`MIXED_AMMO_AND_TIMED_HANDLING_DESIGN.md`](MIXED_AMMO_AND_TIMED_HANDLING_DESIGN.md)。
3. 客户端最多只能提出“库存槽位 + 当时预览的 ItemStack 身份”；服务器必须重新读取该槽位，并在开始 reload 和真正动画 feed 点再次验证 family、ammo、容量、器件类型、余弹和完整 ItemStack 组件。
4. 选中物品被移动、替换、装空、变成不兼容或动画中断时必须 **fail closed**：不转而选择另一只弹匣、不回退为散装弹、不静默扣除其他库存。
5. 只有真实服务器 reload 事务成功预留后，才可播放相应的原枪包换弹动作；轮盘不制造不存在的动画 feed 点。

## 明确不自动覆盖的机制

第一版（如果重新获准实现）至多考虑已经启用且经审计的 `detachable_magazine` 与 `belt`。以下机制继续使用各自的真实路线，不能因为有一个选择 UI 就被伪装成可拆卸弹匣：

- 桥夹 `stripper_clip`：向固定仓转入，保留余弹和空夹；
- 漏夹 `en_bloc_clip`：独立安装状态、逐发扣除、空夹真实弹出；
- 快装器 `speedloader`：仅在已审计的完整转轮装填动作中使用；
- 管状仓、转轮、固定内仓、单发和所有 `legacy` 路线。

`reload.type = magazine`、枪名、命名空间、模型、弹匣井骨骼、`GunIndex` class 或一张猜测 JSON 都不是把未知第三方枪加入轮盘的证据。

## 实现前置条件与验收

恢复开发前必须先具备并实测：

1. 对目标供弹机构有服务端预留、动画 feed 点和库存提取的完整审计；
2. 多弹种完成独立 `AmmoId`、独立载具、独立装填校验和服务端弹道后，再把不同弹种身份列为候选；
3. 客户端、专用服务器、JEI/REI 和实际 Gunsmith/制造输出均使用同一份供弹定义；
4. 至少覆盖：短按 R、长按后取消、精确槽位选择、动画中移动载具、满背包、重连、创造/无限换弹、`Shift + R`、多弹种、候选超过一页和手柄输入；
5. Windows 本地完成 `./gradlew build` 与游戏内回归后，才能声称功能完成。

在这些前提满足且再次取得交互确认之前，保留本文档，维持即时单点 R 换弹。
