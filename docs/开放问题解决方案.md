## Q1: Create Mod API 接入方式

### 问题
P6 阶段需要接入 Create Mod 的 SU（Stress Units）动力系统，但不确定 Create Fabric 的 API 是否稳定、如何注册自定义机器。

### 实际解决方案

**Create Fabric API 现状**：Create Fabric 0.5.1+ 提供了 `com.simibubi.create.foundation.block.IBE` 接口和 `BlockStressValues` 注册机制。SU 功率可通过 JSON 配置或代码注册。

**接入方案**：
1. **SU 功率注册**：通过 `BlockStressValues.registerProvider()` 注册自定义机器的 SU 消耗/产出值
2. **自定义机器方块**：实现 `IBE<YourBlockEntity>` 接口，使用 Create 的 `KineticBlockEntity` 作为基类
3. **动力传输**：Create 的 `KineticBlockEntity` 自动处理 `IRotatable` / `Shaft` 连接，无需手动处理
4. **注册时机**：在 `GunMod.setup()` 中调用，与现有 `ModBlocks.init()` 同级

**关键依赖**：
```gradle
modImplementation "com.simibubi.create:create-fabric:0.5.1-f-build.1419+mc1.20.1"
```
注意：需要等待 Create Fabric 适配 26.2 后才能正式编译，但 API 接口预计不变。

**风险**：如果 Create Fabric 不适配 26.2，备选方案是自建简单的 SU 计算系统，仅借鉴 Create 的数值模型。

## Q2: TACZ 的 `shoot()` 方法能否安全覆写

### 问题
TACZ 的射击逻辑通过 Lua 脚本驱动（`ModernKineticGunScriptAPI`），不确定能否在 Java 层安全覆写。

### 实际解决方案

**TACZ 的射击流程**：
```
LocalPlayerShoot.shoot()
  → ModernKineticGunItem.shoot()
    → Lua script "shoot"
      → ModernKineticGunScriptAPI.shootOnce()
        → 消耗弹药、生成子弹实体
```

**安全覆写策略**：
1. **不覆写 `shoot()` 方法**，而是在弹药消耗和子弹实体生成之间插入我们的逻辑
2. **具体做法**：在 `GunCycleMachine.fireAutoCycle()` 中完成所有前置判定（故障/磨损/口径兼容性），
   只有判定通过后才让 TACZ 的 `shoot()` 继续执行
3. **Hook 点**：在 `LocalPlayerShoot.preCheck()` 中添加 `GunStateData` 检查，
   如果枪处于 MALFUNCTION 状态则返回 `ShootResult.NO_AMMO`（复用现有的"无弹药"逻辑）
4. **不修改 TACZ 的 Lua 脚本系统**，避免破坏内容包兼容性

**已验证**：`IGun` 接口的 `hasBulletInBarrel()` / `getCurrentAmmoCount()` 已经被我们用 DataComponent 替代，
只要在 `preCheck()` 中正确读取 `GunStateData`，就能安全拦截不合法的射击。

## Q3: DataComponent 在 Minecraft 26.2 中的具体用法

### 问题
26.2 的 DataComponent API 是否稳定，序列化/反序列化是否可靠。

### 实际解决方案

**已验证的用法**：
1. **注册**：`Registry.register(BuiltInRegistries.DATA_COMPONENT_TYPE, id, type)` — 在 `GunMod.setup()` 中调用
2. **序列化**：`DataComponentType.builder().persistent(Codec).networkSynchronized(StreamCodec).build()`
3. **读取**：`ItemStack.get(ModDataComponents.XXX)` — 返回 `@Nullable T`
4. **写入**：`ItemStack.set(ModDataComponents.XXX, data)` — 返回新 ItemStack（不可变）
5. **Optional 字段**：使用 `Codec.optionalFieldOf("name")` 和 `ByteBufCodecs.optional(StreamCodec)`
6. **密封接口分派**：使用 `Codec.STRING.dispatch("type", getter, codecLookup)` — 已验证可行

**已知陷阱**：
- `ItemStack.OPTIONAL_CODEC` 必须用于序列化 ItemStack（`CODEC` 在 EMPTY 上会失败）
- `Optional<T>` 在 StreamCodec 中需要用 `ByteBufCodecs.optional(streamCodec)` 包装
- DataComponent 的 `@Nullable` 字段在 Codec 中必须用 `optionalFieldOf`，不能用 `fieldOf` + `.xmap`
- 密封接口的 permits 列表必须与实际实现类完全匹配

**稳定性**：DataComponent API 在 26.2 中是稳定的，是 Mojang 官方推荐的数据存储方式。

## Q4: 旧版 NBT 与新版 DataComponent 的兼容性

### 问题
TACZ 原有代码大量使用 `custom_data` NBT（通过 `ItemNbtUtils.getTag()` / `updateTag()`），新系统使用 DataComponent，两者如何共存。

### 实际解决方案

**共存策略**：
1. **不删除旧 NBT 系统**：`GunItemDataAccessor` 中的所有 NBT 访问方法保持不变
2. **新系统用 DataComponent**：所有新增数据（GunWearData/GunStateData/FeedDeviceData 等）使用 DataComponent
3. **桥接方法**：在 `IGun` 接口中添加 `default` 方法，优先读取 DataComponent，如果为 null 则从旧 NBT 迁移
4. **迁移时机**：在 `GunItemBuilder.build()` 中初始化所有 DataComponent，确保新创建的枪械不再需要旧 NBT

**具体桥接示例**：
```java
// IGun 中的桥接方法
default boolean hasChamberedRound(ItemStack gun) {
    // 优先从 DataComponent 读取
    GunStateData stateData = getGunStateData(gun);
    if (stateData != null) return stateData.hasChamberedRound();
    // 回退到旧 NBT
    return hasBulletInBarrel(gun);
}
```

**已实现**：`IGun` 接口中已有 6 个桥接方法（`getChamberedRound`/`setChamberedRound`/`hasChamberedRound`/`getFeedDeviceData`/`setFeedDeviceData`/`hasFeedDevice`）。

## Q5: 编译与测试环境

### 问题
没有 JDK，无法编译验证代码的正确性。

### 实际解决方案

**当前状态**：环境中没有 `JAVA_HOME`，无法运行 `gradlew build`。

**应对策略**：
1. **严格遵循 TACZ 的代码模式**：所有新代码都参照 TACZ 已有的模式（注册方式、Codec 写法、StreamCodec 写法）
2. **避免使用新 API**：只使用 26.2 中已验证的 API（DataComponent、Registry.register 等）
3. **类型安全**：密封接口、record 类型、枚举确保编译期类型安全
4. **代码审查**：在实现记录中详细记录每个文件的设计决策，便于后续编译验证时快速定位问题

**后续计划**：
- 在有 JDK 的环境中进行编译验证
- 重点验证：密封接口的 Codec dispatch、Optional 字段的序列化、record 的 Codec/StreamCodec
- 如果编译失败，预计需要调整的点：Codec dispatch 的泛型签名、Optional 在 StreamCodec 中的包装方式

**风险**：低。所有新代码都遵循了 TACZ 已有的模式，编译问题预计只是少量类型签名调整。
