## 2. 【重要更正】交接文档 §0.2 的「items JSON 前置缺口」在本分支**不存在**

交接文档用 `git ls-tree -r origin/26.1.2 | grep "assets/lrtactical/items"`
（空）得出「两条分支一个 items JSON 都没有，E 单元被挡」的结论。
**这只看到了 git 跟踪层，漏掉了本分支的资源打包机制：**

- `build.gradle` 的 `processResources` 会把
  `resources/tacz-26.1.2-source-and-resource-bundle.jar`（53 MB 资源 bundle）
  解包进构建输出，`src/main/resources` 下的显式文件优先
  （`DuplicatesStrategy.EXCLUDE`，source-set 的 from-spec 先于 bundle 注册）。
- bundle 里**本来就带着** `assets/lrtactical/items/{melee,throwable,consumable,detonator}.json`
  与 `assets/lrtactical/models/item/{melee,throwable,melee_dynamic,throwable_dynamic,consumable}.json`，
  共 9 个文件，**逐个与 26.2 基线（`7f6d1bf`）逐字节一致**（解包 diff 核对）。
- 该 bundle 的 blob 在 `26.2(main)` / `26.1.2` / `1.21.11` 三条分支上**完全相同**
  （`e7e6adb3…`）。所以「缺口」在 1.21.11 侧同样不成立 —— 那批 items JSON 也
  在那条分支的构建输出里。1.21.11 侧的 `processResources` 还额外做了
  `overriddenBySource.each { exclude it }`，src 优先语义更明确。
- 因此近战/投掷物的 `dynamic_item` 分流入口在这两条分支的**运行时**是存在的；
  交接文档「那两支的近战/投掷物目前就没有走 dynamic_item 分流的入口」不成立。

**后果**：E 单元在本分支没有被挡住，已完整移植。唯一需要 git 新增跟踪的是
`models/item/consumable_dynamic.json`（bundle 里没有）和更新后的
`items/consumable.json`（bundle 里是旧版无分流版本；git 跟踪版遮蔽它）。
两个新 JSON 都过了 `json.load`，其中 `consumable.json` 的 `base` 指向的
`lrtactical:item/consumable_dynamic` 与 `on_false` 指向的
`lrtactical:item/consumable` 现在都能解析。

> 对 1.21.11 侧移植 AI 的提示：先按上面的 bundle 证据复核你们那条分支，
> 再决定 E 单元的实现路径；交接文档里「若属版本契约不同 → E 不适用」的
> 分支条件大概率不触发（1.21.11 ≥ 1.21.2，items JSON 契约同样存在，
> 且 bundle 已带齐 9 个文件）。

## 3. 26.1.2 特有的三处适配（其余逐字节等同源提交）

1. **`LrClientAssetsManager`**：本分支原有写法与 26.2 基线不同 ——
   两个 getter 用三元表达式、两个 `findUnique*DisplayByPath` 带
   `xxxDisplay == null` 前置判空。`git apply --3way` 保留了这些本地写法；
   新加的 `getConsumableDisplay` / `findUniqueConsumableDisplayByPath`
   **按本分支风格补齐**：getter 用三元、path 回退加判空（与另两个
   findUnique 方法一致，避免第三个成为例外）。
2. **`DisplayTransform` 类注释**：源注释写「26.2 的 `ItemTransform#apply`
   自带 `translate(-0.5,-0.5,-0.5)`」。已对本分支 merged jar 的
   `ItemTransform#apply(Z, Pose$Pose)` 字节码逐指令确认：**26.1.2 同样自带
   两次 `±0.5` 平移**（代码里 `ldc -0.5f ×3 → Pose.translate(FFF)` 出现两次，
   中间依次做 translation → rotationXYZ(×DEG_TO_RAD) → scale）。
   手写三步平移的结论不变，注释改为「26.x（26.1.2 与 26.2 均如此，26.1.2
   已字节码确认）」。
3. **`items/consumable.json`**：本分支原本不 git 跟踪该文件（bundle 提供），
   源补丁无法直接 apply；已按源提交 post-image 新建为 git 跟踪文件
   （遮蔽 bundle 旧版，见 §2）。

## 4. 符号级核对（26.1.2 merged jar，逐 classfile 常量池/字节码）

本沙箱**无 JDK 且无法获取**（见 §6），`compileJava` 跑不了；
以下结论与 26.2 侧「静态核对」同等强度，均针对
`minecraft-merged-0d09a28b48-26.1.2.jar`：

**单元 C（最容易踩的跨版本坑，全部排除）：**

- `Particle#getLightCoords(F)I` 在 26.1.2 存在且为 **protected**
  —— 交接文档 §3 C 的方法名陷阱（1.21.11 是 `getLightColor`）**在本分支
  不存在**，`@Override protected int getLightCoords(float)` 可编译。
- `getBrightness(LightLayer, BlockPos)I` 是 `BlockAndLightGetter`
  （26.1.2 里是 interface）上的方法；`Level` 本身不直接声明/实现它，
  调用链为 `ClientLevel → Level → LevelAccessor → CommonLevelAccessor →
  LevelReader → (implements) BlockAndLightGetter` —— `this.level`
  （`Particle.level`，protected `ClientLevel`）沿链可达。
- `Particle.x/y/z` 为 protected double（子类访问合法）；
  `BlockPos.containing(DDD)`、`BlockPos.relative(Direction)`、
  `LightLayer.SKY/BLOCK`、`Direction.values()` 均在。

**单元 D/E：**

- `RenderTypes` 在 26.1.2 同样是 `net.minecraft.client.renderer.rendertype`
  包（复数名），`entityCutout(Identifier)` / `entityTranslucent(Identifier)` 在。

  与本仓既有调用 `poseStack.last()` 一致（`MeleeItemRenderer` 同款，既有代码）。
- `SubmitNodeCollector#submitCustomGeometry`：接口定义在 Fabric API

  既有调用点（`BedrockModel`、`MeleeItemRenderer` 等），模式逐字一致。
- `Mth.lerp(FFF)` / `Mth.clamp(FFF)` / `Mth.DEG_TO_RAD`、
  `ItemDisplayContext.GUI` / `firstPerson()`、

## 6. 验证状态 —— **未编译，不得标 PASS**

- **`./gradlew compileJava` 本环境跑不了**，原因（均已实测）：
  1. 沙箱无 JDK，且所有 JDK 下载源不可达
     （adoptium / temurin github release CDN / corretto / azul / oracle 均为
     SSL 阻断；可达 host 仅 github.com / api.github.com / codeload /
     pypi.org / npmjs，PyPI 上无 JDK 25 分发）；
  2. Gradle 9.5.1 发行包（services.gradle.org）不可达，本地无缓存；
  3. maven.fabricmc.net / plugins.gradle.org / maven central / modrinth /
     curse 全部不可达，依赖无法解析。
  即使有 JDK 也走不到编译阶段。
- 已做：§4 的符号级逐条核对 + 贴入后与源提交 post-image 的 blob 比对 +
  JSON 校验。强度等同源分支的静态核对，**不等于编译通过**。
- 有 JDK 的机器上至少应跑：`./gradlew compileJava`（本批无新增 mixin，
  无 refmap 问题；`verify_mixin_targets.py` 是 1.21.11 分支的脚本）。
- 用户实机复测前，任何文档/发布文案不得写 PASS 或 "fixed"。
