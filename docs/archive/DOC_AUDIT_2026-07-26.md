### 0.1 关于工具：沙盒无 JDK，我自建了 javap 等价物

本沙盒**没有任何 JDK**（`java: command not found`），且 Adoptium / Maven Central / Modrinth API / raw.githubusercontent 全部**网络不可达**（仅 `github.com`、`codeload.github.com`、`pypi.org` 通）。因此 HANDOVER §1 教的 `javap` + Vineflower 流程在本环境**跑不起来**。

我改用 Python `javatools` 库直接解析 class 文件，自建了一个 javap 等价工具（`/home/user/.scratch/mcq.py`，会话内可复现）：

```
members <class>        # 等价 javap -p：列字段+方法签名
refs <class> <method>  # 等价 javap -c：反汇编并解引用常量池
grepm <regex>          # 全 jar 方法/字段索引搜索
callers <substring>    # 反查调用点
```

**能力边界（必须说明）**：这套工具给出的是**字节码事实**（签名、常量、调用目标、控制流跳转），足以判定「方法存不存在」「常量是多少」「谁调用了谁」「分支条件是什么」。它**不产出 Java 源码**，所以涉及复杂表达式语义时我会标注为「据字节码推断」而非「已确证」。

> ⚠️ 沙盒 `/tmp` 会在轮次间被清空，工具已重建在 `/home/user/.scratch/`（未纳入 git）。

## 2. ❌ 证伪：唯一一条会导致误修的硬错误

### 2.1 `Entity.moveDist` 对**远程玩家恒为 0** —— r6/r7 的核心前提在多人环境不成立

**文档说法**（`PROGRESS_ROUND6.md` §②、`ROUND7.md`、`HANDOVER.md` §1.5 速查表）：

> 26.2 把 `walkDist` 更名为 `Entity.moveDist`，「语义与旧 `walkDist` 完全一致，因此改用它」，增量仍是 `+= 水平位移 * 0.6`。

**字节码事实**：更名一半对，但**写入条件被 26.2 加了门禁**，文档完全没提。

`Entity.moveDist` 唯一的写入点在 `Entity.applyMovementEmissionAndPlaySound`（偏移 54→70，`getfield moveDist` → `fadd` → `putfield moveDist`），而它在 `Entity.move` 里的调用（偏移 648）被这样包着：

```
605  invokevirtual  Level.isClientSide()          // 客户端？
608  ifeq  (10,)
611  invokevirtual  Entity.isLocalInstanceAuthoritative()   // ← 关键门禁
615  ifeq  (36,)                                   // 不满足 -> 整段跳过
...
648  invokevirtual  Entity.applyMovementEmissionAndPlaySound(...)  // 才写 moveDist
```

再把门禁展开（全部来自字节码）：

```
Entity.isLocalInstanceAuthoritative():
    if (level.isClientSide()) return isLocalClientAuthoritative();
    ...
Player.isLocalClientAuthoritative():  return isLocalPlayer();
Player.isLocalPlayer():               return false;   // iconst_0 —— 基类恒 false
LocalPlayer.isLocalPlayer():          return true;    // iconst_1 —— 只有本地玩家
```

**结论**：在客户端，`moveDist` **只对 `LocalPlayer`（本机玩家自己）累加**。对 `RemotePlayer`（其他玩家）`isLocalPlayer()` 返回 `false` → 门禁不通过 → `moveDist` **永远保持 0**。

**这意味着什么**：
- r6/r7 的修复对**第一人称/自己**是正确的（本机是 LocalPlayer）；
- 但**其他玩家的持枪行走动画在多人游戏里会完全静止**（驱动量恒 0，`(0 % 2.0)/2.0 = 0`，动画卡在第一帧）。

**26.2 给出的正确替代品**（这才是原 `walkDist/walkDistO` 的真正继任者）：

```
net.minecraft.client.entity.ClientAvatarState:
    private float walkDist;
    private float walkDistO;
    public void  addWalkDistance(float)                    // walkDist += v
    public void  tick(Vec3, Vec3)                          // walkDistO = walkDist  ← 每 tick 保存前值
    public float getInterpolatedWalkDistance(float pt)     // Mth.lerp(pt, walkDistO, walkDist)
    public float getBackwardsInterpolatedWalkDistance(float pt)
```

驱动方（字节码确认）：`AbstractClientPlayer.addWalkedDistance(f)` → `clientAvatarState.addWalkDistance(f)`；`LocalPlayer.move` 末尾 `Mth.length(dx,dz) * 0.6F` → `addWalkedDistance`。**量纲与旧 `walkDist` 完全一致（同样是 ×0.6）**，且 `getInterpolatedWalkDistance` 就是上游那句手写插值的官方版本。

访问路径：`AbstractClientPlayer.avatarState()`（public）。vanilla 自己在 `AvatarRenderer.extractCapeState` 里就是这么用的。

**建议**（未实施，仅诊断）：`GunAnimationStateContext#tacz$walkDistance` 改为——若实体是 `AbstractClientPlayer` 则走 `avatarState().getInterpolatedWalkDistance(partialTicks)`，否则回退现有 `moveDist` 逻辑。这样可以**整个删掉** `IMoveDistTracker` + `EntityMixin` 的 tick 钩子（r7 自建的那套 `moveDistO` 重建机制），因为 26.2 官方已经提供了等价物。

> ⚠️ 我**没有改代码**。理由与 r11/r15 作者的判断一致：这条链路涉及多人同步语义，沙盒无 GPU 无法验证，且「其他玩家动画静止」这个推论需要实机确认（本机自测**看不出来**——你自己的动画是正常的）。请优先在多人环境下观察**其他玩家**的持枪行走动画。

## 4. ⚠️ 部分属实 / 结论过宽

### 4.1 「26.2 彻底移除 stencil」—— 结论对，但论据不完整

r9/r10 的实际影响（stencil 不可用、必须走 PIP）**成立**，我确认：
- `RenderSystem` 中 `stencilFunc/stencilOp/stencilMask/clearStencil` **全部不存在**（grep 零命中）；
- `DepthStencilState` 只有 `depthTest / writeDepth / depthBiasScaleFactor / depthBiasConstant` 四个字段，**无任何 stencil 字段**；
- `RenderTarget` 只有 `depthTexture / depthTextureView`。

但文档漏了一点：`GpuFormat` 里**确实还有** `D32_FLOAT_S8_UINT`、`D24_UNORM_S8_UINT`、`S8_UINT` 三个枚举常量，且有 `hasStencilAspect()` 方法。r9 提了一句「用不上」，但没说清 —— 准确表述应是：**格式层保留了 stencil 附件的描述能力，但管线层没有任何 API 能配置比较函数与操作，所以无法使用**。这个区别在将来 Mojang 补回 API 时会变得重要。

### 4.2 `RenderTarget` 上有本 mod 自己注入的接口 —— 文档未提，排查时容易误判

字节码显示 26.2 的 `RenderTarget` 是 `implements cn.sh1rocu.tacz.api.mixin.RenderTargetStencil`。这**不是** Mojang 的东西，是本仓库通过 `fabric.mod.json` 的 `loom:injected_interfaces` 注入的（同理 `LivingEntity` 被注入了 `ItemHandlerCapability`）。

我核查时一度以为找到了 26.2 残留的 stencil 支持。**文档里完全没提这套 injected_interfaces 机制**，建议在 HANDOVER 补一句，否则下一个人反编译时会踩同样的坑（尤其是本地 loom 缓存的 jar 已被 remap 过、带着注入痕迹）。

### 4.3 r19 的「地形不看 override」结论正确，但要补一个前提

r19 说 `ChunkSectionsToRender#renderGroup` 硬取 `renderTarget.getColorTextureView()`、不看 `outputColorTextureOverride`。**字节码确认属实**（偏移 78 `outputTarget()` → 97 `getColorTextureView()` → 111 `createRenderPass`，全程无 override 判断）。

但要注意：r19 由此推荐的「方案 A = Mixin 临时替换 `GameRenderer.mainRenderTarget`」，字节码显示 `mainRenderTarget` 是 **`private final`** 字段。Mixin 改 final 字段需要 `@Mutable` + Accessor，或者改 `mainRenderTarget()` 方法的返回值（`@Inject` + `cir.setReturnValue`）。后者更安全。文档没说这个细节，实施时会卡一下。

`TextureTarget` 的构造函数确认为 public：`(String label, int w, int h, boolean useDepth, GpuFormat)` —— r19 说「可以直接 new」属实。

### 4.4 「副手开枪是上游设计、非移植缺陷」—— 属实，已交叉验证

上游 1.21.1 `ShootKey.java` 第 41 行确实是 `ItemStack mainHandItem = player.getMainHandItem();`。r3 的结论成立。

## 9.6 【更正】该移植版未开源，但**代码是 GPLv3** —— 结论反而对我们有利

用户反馈：「这位作者仿佛没有开源的打算，无法在 GitHub 上找到该项目」。
我核实了，**属实**：

- GitHub 全站搜索 `tacz` 的 30 个仓库中**没有** guilhermez1989 的任何条目；
- `search/users?q=guilhermez1989` **零结果**（该用户在 GitHub 上可能根本不存在）；
- CurseForge 项目页**没有 Source / Issues 链接**（对比：`MUKSC/TaCZTweaks`、
  `Sh1roCu/TACZ-Refabricated` 都挂了 GitHub）；
- 作者其余 4 个项目（Prismanium、Radiant Gear NeoForged、Player Tracker Reworked、
  TaCZ Controlify Compatibility）**同样没有公开仓库**。

### 但这里有一个关键事实：它的许可证是 GPLv3

CurseForge 项目页元数据明确标注：

> **License: GNU General Public License version 3 (GPLv3)**  ·  Project ID 1573653

这和我上一轮的说法**不一致，我更正如下**：

| | 上一轮我说的 | 实际 |
|---|---|---|
| 代码许可 | 「CC BY-NC-ND，ND=禁止演绎，法律上不干净」 | ❌ **说错了**。CC BY-NC-ND 4.0 约束的是 TACZ 的**美术/音频资产**；**代码是 GPLv3** |
| 能否参考代码 | 「不建议抄」 | ✅ **GPLv3 明确允许衍生**，条件是衍生作品同样以 GPLv3 发布并提供源码 |

**本项目正好满足这个条件** —— `fabric.mod.json` 里写的就是
`"license": "GPL3 / CC BY-NC-ND 4.0"`（代码 GPL3 + 资产 CC），
与上游 TACZ、与该 NeoForge 移植版**三者的代码许可完全一致**。

### 所以真正的结论是

**「没开源」在法律上并不构成障碍，只构成不便。**

GPLv3 的 §6 要求分发二进制时必须向接收者提供对应源码。也就是说：

- 该作者以 GPLv3 分发了 jar，**就有义务在被索取时提供源码**（GPLv3 §6 "Conveying Non-Source Forms"）；
- 即便他不主动开源，**你作为接收者有权向他索要源码**；
- 退一步，**反编译该 jar 用于理解与互操作，在 GPLv3 语境下也不存在授权障碍**
  —— 它本来就授予了你研究和修改的权利。

真正的障碍只有一个：**本沙盒下载不到那个 jar**。
已试 `mediafilez.forgecdn.net`、`edge.forgecdn.net`、CurseForge 下载 API、
Curse Maven（`curse.maven:tacz-port-1573653:8239554`），**全部返回 000**（网络不可达，非 404）。

### 给你的可选项（按性价比排序）

| 方案 | 成本 | 说明 |
|---|---|---|
| **A. 你手动下载 jar，放到仓库外目录** | 最低 | 我用同一套 `mcq.py` 反编译对照它怎么解 26.x 的渲染管线。**推荐** |
| B. 向作者索要源码 | 低 | GPLv3 §6 赋予你这个权利；CurseForge 评论区可直接问 |
| C. 不管它，自己推进 PIP | 零 | 我们目前**已经领先它**（见下） |

### 一个反直觉但重要的判断：我们未必需要它

三条理由：

1. **版本更旧**：它是 26.1.2，我们是 26.2。26.1→26.2 之间仍有渲染改动，
   它的写法不能照搬。
2. **加载器不同**：NeoForge 的事件总线/注册/Mixin 组织方式与 Fabric 差异很大，
   真正能复用的只有「Mojang 侧 API 怎么调」这一层 —— 而这一层**我已经用字节码
   直接从 26.2 jar 里读出来了**，本来就不需要经过第三方转述。
3. **它的完成度未必更高**：其评论区（24 天前）报告的
   「瞄具倍率切换失效」，正是本仓库**第 18 轮已修复**的缺陷。
   在这一点上**我们领先**。而它 Beta、无 changelog、1.5K 下载、作者自述
   「Rarely for newer versions like 26.1」，看不出会持续维护到 26.2。

**综合建议**：把它降级为「**有则更好、无则无妨**」的可选参考，
不要让 PIP 的推进依赖它。如果你愿意手动下一次 jar，我可以做一轮对照；
不下也不影响后续工作。
