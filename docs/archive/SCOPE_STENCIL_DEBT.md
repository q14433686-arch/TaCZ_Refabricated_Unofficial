# 瞄具渲染的结构性债务 —— 为什么会「叠叠乐」

**日期**：2026-07-27（第 35 轮）
**触发**：用户实测后指出——

> 「或许和上一点是同构的，你也照样没给是否剔除高倍的镜组做门禁，
> 不过这或许不是这个问题，而是揭示了我们这种低成本替代方案的必然低效和叠叠乐式的bug」

**结论：这个判断是对的。** 本文说明为什么，以及边界在哪。

---

## 1. 两个 bug 确实同构

第 34/35 两轮修的四个瞄具 bug，根因是**同一个**：

| 轮次 | 症状 | 直接原因 |
|---|---|---|
| r34 | 红点开镜后整个消失 | `cullScopeBody` 没分 sight / scope |
| r35 | 组合镜两组准星同时画 | 准星提交没分 sight 组 / scope 组 |
| r35 | 组合镜目镜掏空错乱 | `show = w.isScope && ...` 没看当前激活哪组 |

三处都是「**该分情况的地方用了一个全局布尔**」。改法也雷同：加一个门禁。
这就是「叠叠乐」——每发现一种没覆盖到的形态，就再叠一个 `if`。

---

## 2. 为什么必然如此：stencil 是**空间**分区，布尔是**全局**开关

上游的机制本质是**按屏幕区域**决定每个像素画什么：

```
renderScope():
    渲染 ocular            -> 写模板值 i+1（只写模板，不写颜色）
    stencilFunc(EQUAL, 0)  -> 只在【目镜圆之外】画 scope_body
    stencilFunc(EQUAL, ~(i+1)) -> 只在【目镜圆之内】画 division
```

同一个 `scope_body`，**圆内不画、圆外画**。这是一次绘制里的空间二分。

26.2 的渲染抽象层（`RenderPipeline` / `DepthStencilState` / `VulkanRenderPipeline`）
**完全没有 stencil 概念**——不是"暂时没接"，是 OpenGL 与 Vulkan 双后端的
公共抽象里就不存在（第 25 轮已逐类确认）。我们能做的只有：

```java
part.visible = false;   // 全画 或 全不画
```

**把一个二维的区域判定，压成了一个零维的布尔。** 信息量从「每像素一个决策」
塌缩到「每部件一个决策」，丢失的那部分只能靠人工枚举形态补回来：

- 是筒镜还是红点？→ 一个 `if`
- 是不是组合镜？→ 再一个 `if`
- 组合镜当前用哪一组？→ 再一个 `if`
- 这一组的节点怎么命名？→ 再一个 `if`（而且 vudu 还不遵循命名约定）

形态数量是**枚举**出来的，不是**推导**出来的。所以永远可能有下一个没覆盖到的
枪包/模型——这正是「必然低效」的准确含义。

---

## 3. 当前方案的能力边界（诚实清单）

**能做对的**：
- 单一形态瞄具（纯红点、纯筒镜）的目镜掏空与镜身剔除
- 组合镜按 views 数组切换镜组（前提是模型遵循 `sight_*` / `scope_*` 命名）
- 发光准星的提取与满亮度绘制

**做不到、且加再多 if 也做不到的**：
- **圆形暗角**。上游"圆外黑、圆内透"是渐变的模板圆，布尔开关只能全黑或全透。
  现在开镜是"整个镜筒不画"，所以没有镜筒黑边。
- **两组准星的空间隔离**。真正正确的是"红点准星只出现在红点窗口内、
  筒镜准星只出现在筒镜圆内"。我们只能选一组全画。
  侧挂红点（红点在筒镜斜上方）时，这个近似最明显。
- **镜内不显示枪体**。上游靠模板把镜内区域的枪体几何裁掉，我们没有。
- **不遵循命名约定的模型**。`scope_vudu` 的准星叫 `division_illuminated` /
  `division_2_illuminated`，没有 `sight_` / `scope_` 前缀，无法按前缀归组。
  当前策略是"过滤后为空就退回全集"，即 **vudu 仍会两组同画**。
  这是已知未解，不是已修。

---

## 4. 真正的出路（不是本轮范围）

要根治必须**恢复"按屏幕区域裁剪"这个能力**。26.2 下唯一可行的方向是
**在 fragment shader 里做圆形裁剪**——`discard` + `#ifdef` 是 vanilla
原生手法（`entity.fsh` 的 `ALPHA_CUTOUT` 就是这么写的），
`TextureTransform(String, Supplier<Matrix4f>)` 是 public 构造、
vanilla 用它做附魔光效滚动，属官方扩展点。

但前两次尝试都失败了，**失败原因已经查清且都不是 shader 本身的问题**：

- 第 29 轮：Java 侧用 `Camera#getViewRotationProjectionMatrix` 自己算屏幕坐标，
  而手部 PoseStack 已含视角回摆（本就是相机空间）→ **视角旋转应用了两次**
- 第 31 轮：改为 GPU 投影 + aspect 校正 → 用户判断"不见得有任何更改"

教训记录在 `SCOPE_STAGE2_POSTMORTEM_2026-07-27.md`。**重做的前提是先解决
"圆心屏幕坐标怎么算才对"这一个问题**，而不是再写一遍 shader。

---

## 5. 本轮的立场

继续用布尔近似**是当前的合理选择**——它便宜、可回滚、每次只动一个变量，
而且确实在逐步收敛（用户四轮实测，每轮症状都在减少）。

但要明确：**这是在还技术债的利息，不是在还本金。**
本金是那个被压掉一维的空间判定能力。
在 shader 裁剪跑通之前，瞄具渲染会一直是"能用但不对"的状态，
且每接入一个新枪包都有概率冒出新的形态没覆盖到。

用户的判断准确，不必粉饰。
