## ① 瞄准镜黑方块 —— 已撤销第 9 轮的错误改动

### 我第 9 轮做错了什么

第 9 轮我发现 `division` 节点被 `setHidden(true)`、在 26.2 下再没被绘制，
就"补提交"了它，以为那是缺失的准星刻度。

**这个判断是错的。** 检查真实瞄具模型 `scope_1873_6x_geo.json` 的 `division` 几何后发现，
它根本不只是准星刻度，而是<b>一组巨大的不透明遮挡面</b>：

```
division pivot: [0, 0, -40]
  origin [-14.0625, -37.1875, -111]  size [32, 32,  0]
  origin [  1.9375,  10.8125, -111]  size [32, 32,  0]
  origin [-13.0625,  -6.1875, -111]  size [96, 34,  0]
  origin [-79.0625,  -6.1875, -111]  size [96, 32,  0]
  ... 以及若干细长的十字线
```

这些 96×34 的大面被放在 z = -111 的远处，**设计上就是要被模板遮罩裁掉的**：
上游用 stencil 让它们只在目镜圆形区域<b>之外</b>显示，从而形成"镜筒外一圈黑边 + 镜内透视"的效果。

26.2 没有 stencil，我把它们无遮罩地画了出来 —— 于是变成糊在屏幕上的一大块黑方块，
正是你截图里看到的。**已完全撤销**，并删掉了 r9 新增的 `submitScopeParts` / `submitTempPart`。

（`BedrockRenderSnapshot#captureSubtree` 保留，它本身是正确且通用的工具方法。）

### 关于"真正的镜内渲染"

你的两个诉求我确认如下：

1. **"瞄准镜没有真正的镜片、看不见后面的东西"** —— 属实。
   镜片效果依赖"把世界再渲染一遍到纹理、再贴到目镜上"（PIP），
   或依赖 stencil 做区域裁剪。26.2 已移除 stencil（第 9 轮已逐项反编译确认），
   因此只剩 PIP 一条路。

2. **"瞄准镜优先级不比机瞄高"** —— 这是 `FirstPersonRenderGunEvent`
   里 `aimingNodePath` 的选择逻辑：装了瞄具走 `scopePosPath + scopeViewPath`，
   没装才走 `ironSightPath`。需要与 PIP 一并核对。

**本轮没有实现 PIP。** 理由是它需要：离屏 RenderTarget + 每帧二次世界渲染 +
在延迟提交管线里插入自定义 pass + 处理递归渲染防护，属于独立的大改动；
在没有实机验证手段（沙盒无 GPU）的情况下贸然提交，风险远大于收益 ——
我不想再重复第 9 轮"没验证就改、反而更糟"的错误。

建议作为下一轮的**专项任务**，我会先出方案再动手。

## ② 曳光弹枪口位置 —— 本轮未能定位，如实说明

第 9 轮修好了"摄像机角度硬编码为 0"（那确实是一个真 bug），
但你反馈仍与枪口对不上。本轮排查并**排除**了以下环节：

| 检查项 | 结论 |
|---|---|
| `cacheMuzzlePosition` 实现 | 与上游**逐行一致**（含 FOV 比值换算） |
| 调用时机（模型提交后、`cleanAnimationTransform` 前） | 与上游一致 |
| `muzzleFlashPosPath` 节点缓存 | 正常，取自 `MUZZLE_FLASH_ORIGIN_NODE` |
| FOV dynamics 是否被驱动 | `CameraMixin` 对 `calculateFov`/`calculateHudFov` 的注入有效，签名与 26.2 一致 |
| 每颗子弹只捕获一次偏移 | 与上游一致（`setFirstPersonRenderOffset`） |

一个**尚未证实的怀疑**：26.2 的渲染顺序是
`LevelRenderer.render`（含子弹实体，偏移 405）→ `renderItemInHand`（偏移 507）。
也就是说**实体先于手部渲染**，子弹在其第一帧读到的 `muzzleRenderOffset`
是"上一帧"的值。1.21.1 也是这个顺序，但 26.2 的 extract/submit 拆分可能让
时序差异被放大（例如切枪后第一发、或帧率波动时）。

要继续收敛需要你协助采一个数据点：**同一把枪、静止不动、连续开若干发**，
观察曳光弹起点是否<b>始终偏在同一处</b>，还是<b>第一发偏、后续正常</b>。
- 若"始终偏同一处" → 是 `muzzleRenderOffset` 的量值/坐标系问题；
- 若"第一发偏、后续正常" → 就是上面的时序问题，我按此修。
